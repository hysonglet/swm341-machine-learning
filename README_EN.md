# swm341-ai —— Handwritten Digit Recognition on the SWM341

This project implements **handwritten digit recognition** in Rust on the Synwit SWM341
(STAR-MC1, Armv8-M Mainline + DSP + single-precision FPU, 150 MHz, 512K flash / 64K SRAM +
8M SDRAM). Each `src/bin/` is a small, independently flashable, independently verifiable
milestone.

The operator library is the pure-Rust [`embedded-nn`](https://crates.io/crates/embedded-nn)
0.2.3 (`#![no_std]`, zero heap allocation). Cross-compilation goes through `rustc` only —
no `arm-none-eabi-gcc` / CMake / bindgen needed. The GUI uses
[`oxivgl`](https://crates.io/crates/oxivgl) 0.9.2 (a safe Rust binding for LVGL 9.5; the
underlying `oxivgl-sys` compiles the LVGL C library with cc + bindgen).

## Running it

```bash
# target triple (one-time)
rustup target add thumbv8m.main-none-eabihf

# smoke test
cargo run --bin 00_hello

# operator self-test (RTT print, probe-rs attaches directly in the terminal)
cargo run --bin 01_nn_smoke
# for real speed numbers use release:
cargo run --release --bin 01_nn_smoke

# SDRAM capacity + read/write self-test
cargo run --bin 02_sdram

# on-device inference (run the host tool below first to generate gen/model.bin and gen/samples.bin)
cargo run --release --bin 02_infer

# 2b: SD read PNG → decode → preprocess → infer (see "SD card + PNG" below)
cargo run --bin 03_sd_image

# 5: LCD bring-up
cargo run --bin 04_lcd
# 5+: integrate oxivgl / LVGL 9.5
cargo run --bin 05_oxivgl

# 6: handwritten-digit recognition page (default flash target, built-in sample carousel)
cargo run --bin 06_digit_ui

# 7: stream PNGs from SD card and recognize
cargo run --bin 07_sd_ui

# 8: touch handwriting live recognition (GT911 + drawing pad)
cargo run --bin 08_draw_ui

# build only, no flash
cargo build --release --bins
```

### Train + quantize: run `host/` on the Mac first

```bash
cd host
cargo run --release                 # default 1500 train / 1000 test per class
cargo run --release -- --train 2000 --test 1000   # more data for higher accuracy
```

It draws samples from `../data/by_field.zip`, preprocesses them with **the same**
`core_ml::preprocess` as the firmware, trains a Softmax regression (per hardwrite ch. 6),
per-channel quantizes to int8, and verifies: **int8 test accuracy ≈ float test accuracy
(measured 91.48% vs 91.49%)**. It then exports weights and samples to `../gen/model.bin`,
`../gen/samples.bin`, which `02_infer` bakes into flash via `include_bytes!`.

> Key: host and firmware call **the same `embedded-nn` operator**
> (`fully_connected_per_channel_s8`). So once the quantization is verified on the host,
> the on-device result is guaranteed identical — as long as the 28×28 pixel bytes fed in match.

`swm341-hal` is currently referenced via `path = "../swm341-hal"`; switch to a git dependency
as needed.

> LVGL build dependencies (`.cargo/config.toml`): `DEP_LV_CONFIG_PATH` points to `conf/` for
> `lv_conf.h`; `LVGL_SRC_DIR` points to a locally patched LVGL source tree (default
> `target/lvgl-src/lvgl-9.5.0`) to avoid re-downloading the 97 MB tarball;
> `BINDGEN_EXTRA_CLANG_ARGS` adds the macOS SDK header path. `vendor/oxivgl-build` replaces
> `oxivgl-build`'s default example-image generation (which wastes flash and needs pypng/lz4)
> with a local no-op version. The first LVGL build is slow — that's expected.

## How LCD / LVGL / touch are wired

- **Framebuffer**: SDRAM is partitioned as `0x8000_0000..0x8040_0000` for the Rust heap
  (embedded-alloc), then from `0x8040_0000` a 800×480×2 = 768 KiB LCDC framebuffer
  (`FB_BASE = HEAP_BASE + HEAP_SIZE` in `04_lcd`/`05_oxivgl`), and above that LVGL's stripe
  draw buffer (from `05_oxivgl` on).
- **`flush_cb` port**: LVGL runs in PARTIAL mode and only draws dirty rectangles; `flush_cb`
  copies each 40-line stripe row-by-row into `FB_BASE` and returns immediately on
  `flush_ready` — no double-buffer switch, no interrupt. The cost is one SDRAM→SDRAM row copy,
  fine for 800×480@30fps.
- **Fonts**: LVGL's built-in Montserrat has no Chinese glyphs, so page text is English/digits
  only; font sizes are deliberately limited (`06` only pulls 14/20/36) and unused fonts are
  dropped via `--gc-sections` to save flash.
- **Touch**: `08_draw_ui` polls a GT911 (I2C1, see `swm341-hal/examples/i2c_block.rs`) for
  contact points and maps coordinates linearly to LCD pixels; if mirrored/offset, change
  `TP_SWAP` / `TP_FLIP_X` / `TP_FLIP_Y` at the top of the file, or calibrate `TP_X_MAX/
  TP_Y_MAX` from the RTT first-frame raw coordinates.

## How the operator self-test is designed

**1. "Switch off" the quantization parameters so expectations are hand-computable.**
`embedded-nn::support::requantize(val, mult, shift)` is the identity when
`mult = 0x7FFF_FFFF`, `shift = 0`:

```
(val * (2^31 - 1) + 2^30) >> 31 == val     (holds when |val| < 2^30)
```

So all conv/fc in the self-test use this "1.0 multiplier"; the expected value is then a plain
integer sum, e.g. 4×4 input + 2×2 all-ones kernel → 3×3 window sums
`[14, 18, 22, 30, 34, 38, 46, 50, 54]`. A wrong answer reveals a dimension/zero-point
convention bug at a glance, not "the math is wrong."

**2. softmax against an external ground truth.**
Pull CMSIS-NN's official unit-test `TestData/softmax` inputs and TFLite reference outputs
(`mult = 1077952640, shift = 19, diff_min = -3968`) and compare byte-for-byte; also verify
"probabilities monotonically non-decreasing with input" and "`(out + 128)` sum ≈ 256".

**3. Verify `requantize` itself**, since it's the common base of every fixed-point operator.

> Note: the softmax self-test above is **operator-library level** validation (using
> `softmax_s8` as reference). The firmware's `02_infer` and the recognition pages that follow
> do **not** use `softmax_s8` for probabilities — its scale is non-standard (0.882 floor, can't
> give a true probability). Instead `softmax_confidence` computes a **real f32 softmax**:
> `z = logits * S_out` (`S_out` read from `model.bin` offset 16), then `libm::expf`; the
> predicted class still comes from `argmax(logits)`, independent of the quantization.

## About DSP instructions (important — don't be fooled by the README)

The SWM341's STAR-MC1 has the DSP extension, and `embedded-nn` has an `smlad` inline
assembly block, but it's guarded by `#[cfg(target_feature = "dsp")]`. Measured (rustc 1.93.1):

```
$ rustc --print cfg --target thumbv8m.main-none-eabihf -C target-feature=+dsp
# no target_feature line at all
```

ARM's `dsp` is an unstable target feature in stable rustc and **does not** appear in `cfg`, so
that assembly is dead code on the stable toolchain; even adding `-C target-feature=+dsp` yields
zero `smlad` in the firmware (LLVM also doesn't synthesize SMLAD from this 4-way dot-product
pattern). What actually runs is the **scalar 4-way unrolled** kernel, and the real on-device
cycles/MAC are printed by `01_nn_smoke`.

To actually get SIMD later, three paths: nightly + `arm_target_feature`, hand-write an SMLAD
kernel via `core::arch::asm!`, or go back to the C CMSIS-NN. None affect the upper model code;
get the full pipeline working on scalar first.

### Measured performance (dev build, 150 MHz, scalar kernel)

Real numbers from `01_nn_smoke` via DWT:

| Operator | Shape | cycles/MAC | throughput |
| :--- | :--- | ---: | ---: |
| Fully-connected | 128 → 32 | 11.26 | 13.3 MMAC/s |
| Conv | 16×16×1 → 4×(3×3) | 83.52 | 1.8 MMAC/s |

These are **dev config** (`opt-level="s"`, no LTO) numbers; release (LTO) is roughly faster
still. The conv's 83 cycles/MAC is high — the cost of a scalar per-output-channel loop plus
per-point requantize. A sizing intuition: e.g. first layer 28×28×1 → 8×(3×3) ≈ 49k MAC, at 83
≈ 4M cycles ≈ 27 ms; a whole net (a few conv layers + one 128-wide FC) lands in the
hundreds-of-ms range — fine for a "write → recognize" demo, but don't expect high-FPS video.
For more performance, go back to one of the three SIMD paths above.

`02_infer`'s FC has only 7840 MAC, so raw compute isn't the bottleneck — the camera/screen is;
measured on-device accuracy ≈ 91.5% (consistent with host verification).

## SD card + PNG (for `03_sd_image` / `07_sd_ui`)

Full pipeline: **SDIO enumerate SD card → hadris-fat mount volume (auto-detect FAT12/16/32,
long filenames) → walk root, pick `.PNG` → `miniz_oxide` inflate + hand-written de-filter →
grayscale → `core_ml::preprocess` to 28×28 → `Model::predict`** (logs via RTT, `07_sd_ui`
renders straight to screen).

### Prepare the SD card

```bash
# 1) Format the card as FAT16 or FAT32 (exFAT unsupported).
# 2) Put PNGs in the root (any filename, hadris-fat supports long names): N0.PNG … N9.PNG, or any XXXX.PNG.
#    PNG requirements: 8-bit, non-interlaced (no Adam7), color type 0/2/6 (gray/RGB/RGBA),
#    converted to grayscale before preprocessing. White-on-black handwriting recommended (see below).
# 3) 07_sd_ui convention: test/digit/30/*.png = digit 0, 31/*.png = digit 1, ……, 39/*.png = digit 9
#    (folder name − 30 = true label); the program streams and carousels all directories.
```

> Filesystem is [`hadris-fat`](https://crates.io/crates/hadris-fat) 2.5 (pure Rust, `no_std`
> compatible, FAT12/16/32 read/write + long filenames). `SdCard` implements `embedded_io` 0.7
> `Read`+`Seek` on top of `swm341-hal`'s SDIO, presented to hadris-fat as a random-access byte
> stream; the heap lives on SDRAM.

### Run output

The firmware first prints SDRAM/heap ready, SD card sector count, FAT mount success, then per
PNG: dimensions, an ASCII preview (28×28 character art), predicted digit, and inference cycles.
Most handwritten-digit PNGs are **white-on-black**; `03_sd_image.rs` has `INVERT = true` at the
top to invert into "black-on-white" before preprocessing — if your images are already
black-on-white, set it to `false`.

### Gotchas

* **SDIO init timing copied from `swm341-hal/examples/sdio_block.rs`**: short response is in
  `resp[0]` (not `resp[3]`), RCA is in the **high 16 bits** of the CMD3 response, SDSC cards
  must multiply the block number by 512 for the CMD17/CMD24 address, and the data-phase clock
  must be raised to ~18 MHz before issuing CMD7 (otherwise the data engine times out at the
  identification clock). All of these are aligned in `src/sd.rs`.
* **Heap must `init` after SDRAM powers on** (`src/heap.rs`): wrong order HardFaults on first
  allocation.
* **On macOS, killing `probe-rs` mid-run wedges the STLink USB interface**: `probe-rs run` then
  reports `cannot perform this operation while interfaces are claimed`. Unplug/replug the
  STLink (or restart the debug session) — unrelated to the code.
* **`embedded-io` version conflict**: hadris-io uses 0.7.1 while `swm341-hal` pulls in 0.6.1 via
  embassy, so two versions coexist in the dep graph; the root `Cargo.toml` depends directly on
  `embedded-io = "0.7"` to match, and `SdCardError` must implement `core::error::Error +
  Display` and `impl ErrorType for SdCard`.

## SDRAM notes (gotchas)

* **150 MHz requires `ClkDiv::Div2`**: unrelated to `embedded-nn`, but the SDRAM controller only
  supports up to 140 MHz at `Div1`; running 150 MHz at `Div1` reads/writes garbage.
  `Config::default()` uses `Div1`; `02_sdram` explicitly overrides with `.clk_div(ClkDiv::Div2)`.
* **Size must match the actual board**: the controller's address decode (row/col/bank split of
  `HADDR`) is set by `Config::size`; a wrong value scrambles all reads/writes. `02_sdram`'s
  top-level `CONFIGURED_SIZE` defaults to `Mb8` (SimplSDRAM reference design) — change it for
  other boards.
* **Heap must initialize after SDRAM init**: `HEAP.init()` immediately writes the free-list
  head into that memory; if SDRAM isn't powered yet, it writes garbage and the first allocation
  HardFaults. Order: `Sdramc::new_with_pins` first, then `HEAP.init`.

## Memory budget

release measured (`arm-none-eabi-size`, `opt-level="s"` + LTO):

| bin | text | note |
| :--- | ---: | :--- |
| `00_hello` | 9.2 KB | smoke |
| `01_nn_smoke` | 31.2 KB | operator self-test |
| `02_sdram` | ~25 KB | SDRAM self-test |
| `02_infer` | ~30 KB | on-device inference |
| `03_sd_image` | ~93 KB (debug) | SD + PNG decode |
| `05_oxivgl` | 300+ KB | grows noticeably once LVGL 9.5 is linked in (fonts/widgets) |
| `06_digit_ui` | 300+ KB | recognition page (build.rs trims 12 samples ≈ 9 KB into flash) |

bss is mostly the RTT buffer and SDRAM base-address constants (heap/framebuffer live in SDRAM,
not SRAM). 28×28 input + small model weights (tens of KB) fit in flash with room to spare; the
real pressure is the framebuffer — 800×480×2 ≈ 768 KB, which must use onboard SDRAM, not
`.bss`. `03_sd_image` places the PNG decode buffer and FAT directory on the SDRAM heap
(`src/heap.rs` at `0x8000_0000`, 4 MiB); pages after `05` also place the framebuffer after the
heap. In dev config, `07_sd_ui` (LVGL + FAT + PNG) exceeds 512K flash by ~6 KB without LTO, so
the dev profile also enables `lto = true`, leaving ~17K headroom.
